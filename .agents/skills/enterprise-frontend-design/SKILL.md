# 企业级前端设计

让用户先看懂“当前是什么、什么最重要、下一步做什么”，再追求视觉完成度。输出应像成熟商业软件，不像组件陈列、个人作品或 AI Demo。

本 Skill 已内置固定的产品方法、交互决策与蓝白商务设计体系；不要再叠加其他强风格设计 Skill。尊重用户现有品牌、业务能力和已确认方案，不把局部修改扩大成全站重构。

## 在 Supie 六阶段工作流中使用

本节用于 `$supie-dev` / `$supie-edit` 编排，明确本 Skill 四阶段与项目阶段的衔接；单独调用时仍按下文执行。

- Stage 1 已确认的需求直接复用；页面结构与交互选择仅维护在 `prototype/DESIGN.md`，不再生成重复需求或设计报告。
- Stage 2 使用本 Skill 的需求理解、页面结构和 UI 设计方法，并在 `prototype/` 制作独立 HTML/CSS/JS 原型。这里的“实现”只指可交互原型：使用贴近业务的模拟数据，不接真实后端，不修改生产源码，不安装生产技术栈。状态、增删改与分页必须真的改变原型数据；模拟能力须明确标识，不能声称业务已经接通。
- 默认采用内置蓝白商务体系，已有品牌和用户明确要求优先；不生成三风格拼图或组件展板。仅在结构尚有影响主路径的分歧时确认紧凑线框，已确认内容不重复询问。每张视觉预览只展示一个页面或场景。
- 原型走查后由用户明确确认 `UX APPROVED`，编排器记录到 `.supie/state/current.yaml` 的 `stages["2"]`。结构确认、视觉方向认可和 Agent 自检均不等于最终 UX 批准；本 Skill 的“直接实现”不跳过 Supie 的 UX 与技术路线关卡。
- Stage 3 通过仓库证据确认技术栈和 API 契约。下文 Next.js 体系是新建且未定栈时的建议；已有 Vite/React、Vue 或其他已确认栈沿用现有实现，仅迁移适用的设计与交互规则，不为应用本 Skill 换框架。
- Stage 6 才进入生产前端实现，读取已批准的 `prototype/DESIGN.md`、原型与 `contracts/openapi.yaml`（HTTP 项目），保留信息层级和交互语义，并接入真实能力。原型模拟数据不能作为生产功能完成的证据。
- `$supie-edit` 的局部修正仅应用相关规则；结构性改版先做受影响页面的原型与 UX 确认。沿用已有批准记录；范围或主路径发生实质变化时重新确认受影响部分。

## 先判断任务范围

| 请求 | 做法 |
| --- | --- |
| 新应用、整页新建、结构性改版 | 完整执行四阶段；默认确认一次页面结构，必要时再确认视觉方向 |
| 已确认设计后的实现 | 直接读取确认记录并实现，不重复询问已确定内容 |
| 局部组件或交互修复 | 简要确认任务与约束，只执行相关阶段 |
| 仅评审、线框或视觉稿 | 交付请求范围，不自动进入代码实现 |

## 四阶段工作流

### 1. 理解需求

检查产品说明、目标页面、相关路由、真实数据状态、权限和现有组件。没有现有产品时分析需求，不虚构问题。

先确定：

- 核心用户与使用场景。
- 用户进入页面后要完成的一个主要任务。
- 决定下一步的 1～3 项关键信息。
- 唯一主操作；只读页面可以没有。
- 页面主类型：Overview、Work Queue、Object List、Object Detail、Master–Detail、Editor、Investigation、Analytics、Settings 或 Onboarding。
- 数据规模、使用频率、失败成本和权限中会影响设计的条件。
- “设置、参数、配置”的作用域：平台全局、工作区、对象模板、单个对象或单次执行。

用一句话描述任务：

> 当〔角色〕处于〔场景〕，需要对〔对象〕完成〔判断或动作〕，以得到〔可观察结果〕。

若角色、目标、业务流程或信息优先级存在会改变设计方向的歧义，停下来提出 1～3 个关键问题。普通间距、组件样式等可合理推断的细节不询问。完整方法见 [需求与布局](references/product-layout.md)。

### 2. 设计页面结构

围绕主要任务安排导航、首屏、信息顺序与主路径。将每项内容归为：默认保留、按需展开、下沉到详情/设置、合并或移除展示，并说明入口与返回方式。

先做低保真结构，不讨论颜色和阴影。至少给出：

- 页面主类型与选择依据。
- 导航和页面职责。
- 页面标题、主要工作区、0～2 个辅助区和主操作。
- 主内容结构、内容分组、搜索筛选、操作层级与反馈位置。
- “进入 → 判断 → 操作 → 反馈 → 返回”的主路径。
- Modal、Drawer 或独立页面的选择理由。
- loading、empty、filtered-empty、error、no-permission 的位置。

完整新建或结构性改版默认在此提交一份紧凑线框等待确认；用户已经给出明确结构或要求连续完成时不重复暂停。

### 3. 完成 UI 设计

结构确认后读取 [蓝白商务设计系统](references/design-system.md)，按固定技术栈与视觉规则设计同一个真实业务页面。不要先做组件展示板。

硬性视觉规则：

- 蓝白冷灰、单一品牌蓝、1px 细边框、6～8px 小圆角、极轻或无阴影。
- 白色主工作区，浅冷灰导航，中等信息密度；列表优先，禁止满屏 Card。
- 中文界面不添加无额外信息的英文眉题、英文翻译、副标题或全大写装饰词。API、SDK、模型名等必要技术名词可保留。
- 默认不写解释性小字。仅保留会改变理解或避免错误的范围、口径、约束、后果和恢复信息，并放在相关对象附近。
- 不得把本应删除的说明改成更淡、更小的文字。正文、Label、表格内容不得通过小字号压缩页面。
- 不使用渐变、玻璃拟态、霓虹发光、彩色阴影、巨型 Hero、装饰插画或无业务依据的 KPI/图表。
- 一张视觉预览只展示一个完整页面或一个明确场景；多个页面分别输出，除非用户明确要求拼图或对比图。

只有视觉方向尚未确定、改动范围较大或用户明确要求视觉稿时，才在代表页面的视觉方案上追加确认。当前蓝白体系和参考样例已经获得认可，或用户要求连续完成时，直接实现，不机械暂停。

### 4. 实现并验证

核心体系固定采用 Next.js App Router、React、TypeScript、Tailwind CSS、shadcn/ui、Base UI 与 Lucide React。复杂表格使用 TanStack Table，客户端服务端状态使用 TanStack Query，表单使用 React Hook Form + Zod，业务图表使用 Recharts；当前功能不需要时不为满足技术清单制造表格、缓存、表单或图表。已有项目存在经过确认的等价实现时优先保持一致，不擅自迁移或引入第二套完整 UI 框架。

Server Component 为默认选择，只在确需客户端交互时使用 `"use client"`。接入真实路由、数据、权限、表单校验与错误恢复，不用静态假数据替代已有能力，不创建无动作按钮或虚假成功反馈。

按 [交付检查](references/quality-check.md) 验证相关主路径、异常状态、键盘操作、Light/Dark/System、窄屏和长数据。报告实际运行的验证及尚未验证的缺口；代码阅读或静态图不能证明交互已完成。

## 关键布局决策

### 默认视图预算

一个桌面首屏默认只承担：**1 个主要任务、1 个主操作区域、1 个主要工作区、0～2 个辅助区**。出现多组指标、筛选、按钮、图表或 3 个以上独立功能区时，必须重新整理信息层级；不得靠缩小字体和间距硬塞。

页面类型由用户的主要行为决定，不由顶部是否存在汇总数字决定。主要行为是连续处理任务时，即使顶部有少量状态汇总，仍是 Work Queue；状态数量优先放入分段筛选、Tabs、紧凑统计行或视图切换，不拆成一组 KPI Card。

### Card Gate

Section、List、Table 或普通连续布局能表达时，不使用 Card。Card 仅用于：

1. 可独立理解和操作的业务实体；
2. 必须与周围形成清晰业务边界的对象；
3. 可作为完整对象选择、移动或复用的单元。

单个 KPI、说明文字、标题、筛选、Toolbar、普通状态和同一对象的若干属性不得单独装进 Card。出现 3 个以上并列 Card 时，重新评估 List、Table、Section 或 Master–Detail。

### Modal、Drawer 与独立页面

| 容器 | 使用条件 | 不应承载 |
| --- | --- | --- |
| 居中 Modal / Dialog | 单一 Section、通常不超过 5 个简单字段、无复杂联动、约 1 分钟内完成的创建/编辑、简单设置或确认 | 多 Section、长时间填写或复杂联动 |
| 模态 Drawer | 需要保留背景供参考的快速详情、预览或短暂轻量操作 | 双侧持续操作、通用设置、完整创建/编辑、复杂表单 |
| 非模态 Side Panel / Master–Detail | 需要在列表与详情间连续切换，或持续操作两侧 | 无上下文依赖的短任务、完整复杂表单 |
| 独立页面 | 多字段、多 Section、复杂设置、长编辑、多步骤或需要稳定 URL 的任务 | 短小且完成后立即返回的动作 |

出现 2 个以上业务 Section、异步依赖、代码编辑、大段输入、多步骤、危险配置或草稿恢复需求时，优先独立页面。Drawer 不是“从列表点开”的默认答案，使用前必须说清用户需要同时参考主页面的什么内容。列表中的快速预览可以使用 Drawer；含多个 Tabs、长日志、时间线、可分享内容或稳定 URL 需求时进入独立详情页，Drawer 可提供“查看完整详情”。窄屏可转为独立详情页。

全局、工作区和账户级持久配置默认进入独立 Settings 页面；对象级少量配置留在对象编辑上下文；单次执行参数放在当前任务流程中。作用域未知且会改变路由、权限或保存边界时，先询问用户。

### 页面元素选择索引

先按任务选择结构，再调用对应组件；不要为了展示组件库而增加元素。详细规则见 [需求与布局](references/product-layout.md)。

| 设计问题 | 默认选择 |
| --- | --- |
| 同类对象如何呈现 | 多字段比较用 Table；顺序浏览长内容用 List；真实层级用 Tree；事件过程用 Timeline；连续处理用 Master–Detail；Card 必须通过 Card Gate |
| 内容如何分组 | 连续阅读用 Section；同一对象的平级视图用 Tabs；非必要补充用 Accordion；严格先后流程才用 Steps |
| 搜索与筛选如何出现 | 用户确需查找时才显示搜索；直接显示不超过 3 个高频筛选，高级筛选按需展开，生效条件保持可见 |
| 表格分页如何呈现 | 分页区稳定置于可视工作区底部上方，不紧贴最后一条数据；提供每页 10/20 条切换；页数较多时提供页码输入跳转 |
| 操作放在哪里 | 页面主操作放页头；对象操作靠近对象；行内只留 1～2 个高频动作；低频进入 More；批量操作在选择后出现 |
| 反馈放在哪里 | 字段问题 Inline；区块问题就近；页面阻断用 Alert/Error State；低风险短暂成功才用 Toast；可撤销操作提供 Undo |

Tabs 不得替代表单 Section，Steps 不得用来粉饰长表单，必填字段不得默认藏入 Accordion。Tabs 通常不超过 5 个；超过时重新检查页面职责或导航层级。

分页默认通过 `min-height + flex` 布局停靠在主工作区底部，并保留约 `24～32px` 页面底部安全间距；数据不足一页时，在数据行与分页区之间保留可伸展留白。不要用会遮挡数据的 `position: fixed` 冒充底部布局；只有长滚动页确需持续操作时才考虑无覆盖的 sticky 分页。详细行为见 [需求与布局](references/product-layout.md)。

## 文案与字号底线

- 页面标题通常 `22～24px`，Section 标题 `16～18px`，正文 `14～16px`，表格和 Label 不小于 `14px`。
- 辅助或元数据通常不小于 `13px`；`12px` 仅限极少量、非关键的时间戳或紧凑标记，不能承载说明、错误、约束或操作后果。
- 字号不能替代信息层级。优先删掉无价值文案、折叠低频功能或拆分页面。
- 页面通常只显示一个中文主标题；标题已能说明页面职责时不再添加副标题。
- Placeholder 不能替代 Label；错误、单位、必填和不可逆后果必须清楚可读。

## 输出方式

完整设计只维护一份精简设计记录，不为每个阶段生成重复报告。记录仅包含：任务定义、页面类型、首屏结构、内容去向、容器选择、主路径、关键状态、字号与文案约束；每项使用 1～3 条短句，不复述设计系统。对外先给具体方案或改动，再给必要依据。若只完成到线框或视觉阶段，明确等待确认的对象；不得把“方案已出”描述成“页面已完成”。
