## 2. 交付内容

### 2.1 MineruParser（远端解析器）

`rag-server/.../ingestion/parse/MineruParser.java`（新）：

- 实现 `DocumentParser`，`supportedType()=PDF`——与 PdfBoxParser 同类型**互斥注册**；
- **条件注册**：`@ConditionalOnProperty(name="rag.ingestion.pdf-parser", havingValue="mineru")`。
  未配置时 Bean 不存在，PDF 仍走 PdfBoxParser（默认行为零变化）；
- 调用 `POST {base-url}/file_parse`：手工构造 multipart（JDK HttpClient 无内建支持），
  参数 `files[]`（源 PDF）、`lang_list=ch`、`backend=pipeline`、`parse_method=auto`、`return_md=true`；
- 响应映射：取 `results.<name>.md_content`（多文件按序拼接；本集成单文件调用），
  产出 `ParsedDocument.plain(md, extractHeadings(md))`——Markdown 即产物，标题层级由
  StructureChunker 提取为 titlePath，与 MD 语料同构；页码不支持（page=null，OCR 场景无意义）；
- **失败语义（刻意不静默回退）**：
  - 服务不可达/超时 → `PARSER_UNAVAILABLE`(502，新增错误码)，任务 FAILED，
    failureReason 明确指出 mineru-api 地址与两个处置选项；
  - 远端解析失败（HTTP != 200）→ `INTERNAL_ERROR` + 远端状态码与响应片段；
  - 响应无 results / md_content 空白 → 解析失败（不产生空语料）。
  理由：扫描件回退 pdfbox 只会得到「无文本层」，两条路径都必须诚实暴露，不做静默降级。

### 2.2 配置

| 配置 | 环境变量 | 默认 | 说明 |
| --- | --- | --- | --- |
| `rag.ingestion.pdf-parser` | `RAG_INGESTION_PDF_PARSER` | `pdfbox` | `pdfbox` \| `mineru` |
| `rag.ingestion.mineru-base-url` | `MINERU_BASE_URL` | 空 | 如 `http://localhost:8000`；选 mineru 时必填 |
| `rag.ingestion.mineru-timeout-seconds` | `MINERU_TIMEOUT_SECONDS` | `600` | OCR 较慢，按分钟级给 |

`ErrorCode` + `PARSER_UNAVAILABLE(502)`；`contracts/openapi.yaml` 错误码枚举与上传接口
描述同步（声明 mineru 模式失败语义）。

### 2.3 部署形态

mineru-api 是**独立进程**（独立 Python 3.13 venv），与 rag-server 解耦：

```bash
# Python 3.10–3.13 专用 venv（系统 3.14 不被 mineru 支持）
uv venv --python 3.13 ~/mineru-venv
uv pip install --python ~/mineru-venv/bin/python "mineru[core]"
MINERU_MODEL_SOURCE=modelscope ~/mineru-venv/bin/mineru-api --host 127.0.0.1 --port 8000
```

首次调用自动下载模型（`MINERU_MODEL_SOURCE=modelscope` 走国内镜像源；huggingface 可达时缺省即可）。

### 3.2 联调中发现并修复的缺陷

1. **PDF 解析器重复注册 → 启动失败**：mineru 模式下 MineruParser 与 PdfBoxParser 同时
   注册进 ParserRouter（FileType PDF 冲突，应用拒绝启动）。修复：PdfBoxParser 补充
   `@ConditionalOnProperty(... havingValue="pdfbox", matchIfMissing=true)`，与 MineruParser
   严格互斥——这是单测条件注册用例设计时漏掉的互补面，真机联调抓出。
2. **multipart 字段名**：按仓库 README/源码参数名写作 `files[]`，实测 mineru-api 422
   要求字段名 `files`（FastAPI UploadFile 参数名不带方括号）。已修正并同步单测断言。

> 两条都是「文档/惯例与真实服务不符」类缺陷，印证了第三轮检查单「前置实测」的价值。

## 4. 安装与验收清单（已全部执行通过，留存供复测）

安装（见 §2.3 三条命令）后按序验收：

1. **服务健康**：`curl http://localhost:8000/health` → 200；
2. **服务端切换**：以 `RAG_INGESTION_PDF_PARSER=mineru MINERU_BASE_URL=http://localhost:8000` 重启 rag-server，
   日志出现「MinerU 解析器启用：base-url=…」；
3. **端到端入库**：上传任一扫描件 PDF（纯图片型）→ 任务 COMPLETED →
   解析文本预览含 OCR 出的正文 → 分块 titlePath 正常；
4. **失败语义**：停掉 mineru-api 再上传 PDF → 任务 FAILED 且 failureReason 含
   `PARSER_UNAVAILABLE` / 「MinerU 服务不可达」（而非 SCANNED_PDF_NOT_SUPPORTED）；
5. **回退开关**：去掉 `RAG_INGESTION_PDF_PARSER` 重启 → 文本层 PDF 恢复 pdfbox 路径。

任何一步不符合预期即为本集成存在缺陷（而非安装问题），请回传现象。

## 5. 已知边界

- `backend=pipeline`，未启用 vlm/hybrid（更高精度需 GPU 或远端推理服务，第一版不做）；
- 页码不随 OCR 产物（ParsedDocument.page=null），分块无页码定位；
- 同步 `/file_parse` 模式下，rag-server 的 HTTP 超时（默认 600s）就是解析预算上限；
  超长 PDF 应异步化（MinerU 亦有 `POST /tasks`，本版未用）；
- 图片导出（`return_images`）关闭，纯文本语料不含图；
- MinerU 3.4.x 亦支持 DOCX/PPTX/XLSX 输入，但本版仅将 PDF 路由到 MinerU
  （docx/xlsx 的 POI 路径已验证且更轻量，不切换）。
