# R3-P3 实施记录：文档多版本管理

> 状态：实施完成（2026-09-15）。真机验证发现并修复 3 个并发正确性缺陷（见 §3），
> 真机语义验证与回归测试全部通过（§5）。

## 1. 要解决的问题（来源：round2 计划 §1.4-3 / §3 P3）

- 同 KB 内容去重（`UNIQUE(kb_id, content_sha256)`）使「更新文档」只能删除重传；
  删除导致 docId/chunkId 全变 → 会话 citations 悬空、评测数据集锚点失效；
- 无历史版本：旧内容删后不可恢复、不可回滚、不可追溯「答案引用的是哪一版」。

## 2. 方案（最小改动，同表自引用）

### 2.1 数据模型

**不新建表**。`document` 表加三列（Flyway V3）：

| 列 | 类型 | 语义 |
| --- | --- | --- |
| `root_id` | CHAR(36) NOT NULL | 同源文档组标识；指向组内第一版的 document.id。第一版 `root_id = id`（存量回填天然成立） |
| `version_no` | INT NOT NULL | 组内版本号，从 1 递增 |
| `is_active` | BOOLEAN NOT NULL DEFAULT TRUE | 组内激活版本；同一 `(root_id)` 组至多一个 TRUE（应用层保证 + 组内唯一校验） |

索引：`KEY idx_document_root (root_id, version_no)`、`KEY idx_document_kb_active (kb_id, is_active)`。
存量回填：`UPDATE document SET root_id = id, version_no = 1, is_active = TRUE`。

**刻意保留** `UNIQUE(kb_id, content_sha256)`：同 KB 同内容仍 409（不论是否同源）——
内容完全相同的「新版本」没有信息量，保留原语义可让既有错误码/测试不动。

### 2.2 上传语义（DocumentService.upload）

判定顺序：

1. `UNIQUE(kb_id, content_sha256)` 命中（任意文档）→ 409 DUPLICATE_DOCUMENT（不变）；
2. KB 内存在**同名且已存在版本组**的文档（`name` 相同，取其 root_id，仅匹配激活/任意版本
   的 name 均可——按「组内共享 name」实现）且 `fileType` 相同 → 建新版本：
   - 新 document 行：`root_id` 沿用组 root、`version_no = max+1`、`is_active = TRUE`；
   - 原激活版本置 `is_active = FALSE`；
   - chunkConfig 可随新版本变化（每版本独立入库参数）；
3. 其余 → 新文档组（v1）。

版本创建后新版本照常走异步流水线；**激活状态在上传受理时即切换**（不等流水线完成）——
换取「新版本入库期间旧版本内容仍在 ES、仍可被检索」，避免更新窗口内检索空窗。
新版本 INDEXING 完成后自然取代（它已是激活版）；若新版本解析失败，用户可手动
activate 回旧版（版本切换能力兜底）。

### 2.3 检索过滤（RetrievalPipeline）

阶段 4（filterDeletedDocs）后追加阶段 4.5：过滤 `is_active = FALSE` 的文档命中。
实现复用既有模式：一次 `findAllById` 取命中文档的 active 位，内存过滤。
ES mapping **不动**（避免 reindex；active 是 MySQL 侧元数据）。

### 2.4 版本操作（API）

- `GET /documents/{docId}/versions`：返回版本组列表（docId、versionNo、isActive、status、
  chunkCount、createdAt、sizeBytes、contentSha256）；
- `POST /documents/{docId}/activate`：把指定版本设为组内激活（组内其它版本置 FALSE）；
  仅 COMPLETED/FAILED 版本可激活（QUEUED/PROCESSING 中间态不允许）；
- **删除语义**：删除任一版本 = 现有删除逻辑（该版本 doc 行 + ES 分块 + MinIO 对象）；
  若删除的是激活版本且组内还有其它版本 → 自动激活组内最新的 COMPLETED 版本（无则不激活）。

### 2.5 不改的东西

- chunkId 仍为 `{docId}-c%04d`：版本间天然不冲突（docId 不同）；旧版本 chunkId 在
  其版本未删除期间始终有效，citations/评测锚点不悬空；
- `contentHash` 锚点（P1-3）：版本切换后内容未变的分块哈希不变 → 数据集锚点跨版本可用；
- ES mapping、ingestion 流水线、会话/消息结构。

## 3. 契约变更（openapi.yaml）

- `Document` 增加 `rootId / versionNo / isActive`；
- 新增 `DocumentVersionSummary`、`GET /documents/{docId}/versions`、
  `POST /documents/{docId}/activate`；
- 上传接口描述更新（同名新版本语义；409 仅内容相同）。

## 4. 测试计划

- V3 迁移存量回填（已有文档 → v1 active）；
- 上传：同名不同内容 → v2 且激活；同内容 → 409；不同名 → 新组；
- 检索：v2 入库后旧 v1 不再命中；activate 切回 v1 后 v1 命中、v2 不命中；
- 删除激活版 → 回落最新 COMPLETED 旧版；
- 全量回归。

## 3.5 真机联调与 IT 发现并修复的缺陷（5 个，3 个并发正确性 + 2 个持久化正确性）

1. **active_key 生成列设计缺陷**：`CASE WHEN is_active THEN root_id ELSE id END`——
   第一版（root_id=id）失活后 key=id，与激活新版本的 key=root_id 相同 → 撞
   uk_document_active，新版本永远插不进去。修复：`ELSE NULL`（MySQL 唯一索引对
   NULL 不去重，天然允许多个未激活版本）。
2. **activate 混合 UPDATE 顺序不定**：同批 saveAll 里「激活目标」的 UPDATE 先于
   「失活其它版本」执行 → 撞唯一键。修复：先失活并 flush，再激活目标。
3. **流水线 worker 全字段 merge 回写旧 active 位**：上传事务加载的实体快照被
   worker 长持有，运行中发生版本切换后，INDEXING 完成时 save(doc) 把旧
   is_active=true 写回 → 冲突且任务 FAILED。修复：状态推进改定向 UPDATE
   （updateStatusFields），不回写 active 位。

> 前三条都是「单线程单元测试测不出、必须真机并发才能暴露」的缺陷，与第二轮
> 「QaStreamIT 断连」同类——验证闭环必须包含真实时序。

4. **入库 worker 定向 UPDATE 丢 chunk_count**：为修缺陷 3 引入的定向 UPDATE 只含
   status/stage，终态不再 merge 全字段 → chunk_count 永远为 0（IngestionPipelineIT
   抓住）。修复：定向 UPDATE 加入 chunkCount。
5. **rootId 未初始化**：直接构造实体的内部/测试路径未设置 rootId → NOT NULL 列
   插入失败（6 个 IT 集体报错）。修复：@PrePersist 兜底 rootId=id（未显式归组
   即自成一版组）。

## 5. 实测结果（2026-09-15，真机 + IT）

### 5.1 真机语义验证（dev 环境，真实模型）

| 场景 | 结果 |
| --- | --- |
| 同名不同内容再上传 | 新版本 versionNo+1 并**自动激活**，旧版本失活 ✓ |
| 同内容再上传 | 409 DUPLICATE_DOCUMENT（不论版本组）✓ |
| 版本组列表 | `GET /documents/{id}/versions` 返回组内全部版本（升序、含 active 位）✓ |
| activate 双向切换 | v1↔v2 切换，组内至多一个激活 ✓ |
| 删除激活版本 | 组内自动回落激活最新 COMPLETED 旧版 ✓ |
| 删除时无可回落版本（其余版本 FAILED/PROCESSING） | 不激活任何版本（诚实语义）✓ |
| 并发场景：v1 流水线运行中上传 v2 | 两版本都 COMPLETED、激活位正确——验证 §3-3 修复 |

- 前端：tsc 0 错误、vitest 30/30。

## 6. 已知边界

- 检索过滤在应用层（pipeline 阶段 4.5），ES 中旧版本分块仍存在——查询性能不受影响，
  但 ES 磁盘占用随版本数线性增长（删除版本即释放）；
- citations 中存的是 docId+chunkId：引用历史版本的回答仍指向该版本的 chunkId，
  只要该版本未删除就有效；删除后引用悬空为已知取舍（与第一轮语义一致）；
- 版本组匹配按「KB 内同名同类型」：改名后上传会形成新组（而非新版本），第一版按此简化。
