# 03 技术路线 — 通用知识问答 RAG（第一版）

> 前置：`docs/01-需求理解.md`（已批准需求基线）与 `prototype/DESIGN.md`（已批准 UX）。
> 本文解释"为什么"；`contracts/openapi.yaml` 定义"跨 API 边界是什么"。两者共同构成本阶段交付物，

## 1. 解析后的技术栈与版本选型

用户已锁定：Spring Boot + LangChain4j、Elasticsearch、MySQL、MinIO、Maven、Java 17+、
前端 Next.js + React + TS + Tailwind + shadcn/ui、无 Redis、无登录。本节在锁定范围内给出版本与依赖细节。

| 层 | 选型 | 版本线 | 理由 |
| --- | --- | --- | --- |
| 运行时 | Java（Temurin） | **21 LTS**（满足"17+"） | Spring Boot 3.3 支持 `spring.threads.virtual.enabled=true`。上传流水线与 SSE 流式是典型阻塞 IO（ES/MySQL/MinIO/模型 HTTP），虚拟线程让"一请求一线程/一任务一线程"的最简模型足够用，不必引入 WebFlux 响应式复杂度 |
| 后端框架 | Spring Boot | **3.3.x** | 用户锁定；3.3.x 为成熟稳定线（3.4/3.5 若实现时已稳定可顺延，需在实现计划里重申一次） |
| LLM/Embedding 接入 | LangChain4j `langchain4j-bom` + `langchain4j-open-ai` | **1.x**（BOM 锁定 1.0+ 最新补丁） | `OpenAiChatModel` / `OpenAiStreamingChatModel` 与 `OpenAiEmbeddingModel` 均支持自定义 `baseUrl`，可直接对接 OpenAI 兼容网关（vLLM、Ollama 的 OpenAI 端点、各类中转），满足"模型可配置切换"；只用其模型客户端，不引入其 RAG 高层封装（检索/分块自研，保证可解释与可控） |
| PDF/文本解析 | `langchain4j-document-parser-apache-pdfbox`（PDFBox）+ 内置 MD/TXT 直读 | 1.x 对应版本 | 第一版只需文本型 PDF 正文抽取与标题/页码；比全量 Apache Tika 轻一个数量级。MinerU（第二/三轮）以新 `DocumentParser` 实现接入，接口不变 |
| ES 客户端 | `co.elastic.clients:elasticsearch-java` | **8.14.x**（与服务端 8.x 同代） | 直接用官方 java-client 写 kNN + filter 查询与 bulk 索引；不用 Spring Data Elasticsearch——它对 kNN/自定义 mapping 的抽象反而绕 |
| MySQL 驱动/访问 | `mysql-connector-j` 8.4.x + Spring Data JPA（Hibernate） | Boot 托管 | 元数据 CRUD 简单，JPA 足够；状态机 CAS 更新、批量清理等用 native query 显式写 SQL，不依赖 ORM 魔法。不选 MyBatis：无存量 SQL 资产，团队按 Boot 默认走成本最低 |
| 迁移 | Flyway（`flyway-core` + `flyway-mysql`） | 10.x（Boot 托管） | 用户 profile 指定 flyway；`db/migration/V*.sql` 纯 SQL，MySQL 8 方言 |
| 对象存储 | `minio-java` | 8.5.x | S3 兼容 API，MinIO 官方 SDK |
| API 文档 | `springdoc-openapi-starter-webmvc-ui` | 2.6.x | 运行时导出 `/v3/api-docs`，用于与 `contracts/openapi.yaml` 做漂移检查 |
| 可观测 | `spring-boot-starter-actuator` + Logback（结构化 pattern） | Boot 托管 | health/info/metrics 端点 + 自定义 `ragModels` HealthIndicator；不引 OTel 全家桶（第一版单实例，日志+actuator 够用） |
| 测试 | JUnit 5、Mockito、AssertJ、Testcontainers（mysql / elasticsearch / minio 模块）、`org.openapitools.openapidiff:openapi-diff-core` | 1.20.x / 最新 | 见第 9 节 |
| 前端 | Next.js 14+（App Router）、React 18、TS 5、Tailwind 3、shadcn/ui | — | 用户锁定 enterprise-frontend-design 默认体系；`openapi-typescript` 从 `contracts/openapi.yaml` 生成类型 |

**明确不引入**：Redis/Redisson（第一版单实例，无共享状态需求）；消息队列（见第 10 节）；
Apache Tika 全量包、LangChain4j 的 RAG/AGI 高层模块、OTel、Spring Cloud。

## 2. 模块边界

**Maven 单模块**（`rag-server`）。项目规模（5 个页面域 + 一条流水线）不值得多模块的构建税；
纪律靠包边界与 ArchUnit（可选）维持：

```text
com.rag
├── api/            REST 层：controller、request/response DTO、SSE emitter、全局异常处理、requestId 过滤器
│   ├── kb/  document/  session/  qa/  debug/  eval/
├── service/        应用服务：KnowledgeBaseService、DocumentQueryService、SessionService、EvalService、CleanupService
├── ingestion/      入库流水线（与问答链路物理隔离的包）
│   ├── IngestionTaskManager（线程池调度、CAS 认领、启动恢复）
│   ├── pipeline/   Parse → Clean → Chunk → Embed → Index 各阶段实现 + StageContext
│   ├── parse/      DocumentParser 接口 + PdfBoxParser / MarkdownParser / TextParser   ← MinerU 未来在此新增实现
│   └── chunk/      Chunker 接口 + LengthOverlapChunker / StructureChunker
├── retrieval/      RetrievalService（embedding→kNN→过滤）、ContextAssembler、Reranker 接口（第一版仅 no-op 实现）← BGE 未来在此替换
├── llm/            ChatStreamService（StreamingChatModel 封装、prompt 组装、超时/取消）
├── storage/        ES（EsChunkIndex：索引生命周期 + kNN + bulk）、MinIO（ObjectStore）、MySQL repository
├── eval/           评测执行器（复用 retrieval + llm，不建第三条链路）
├── domain/         实体、枚举、领域异常
└── config/         @ConfigurationProperties（RagProperties）、Bean 装配、启动校验、线程池定义
```

关键边界规则：

1. **入库与问答隔离**：`ingestion` 不 import `retrieval/llm`；两者只共享 `storage` 与 `domain`。
   评测 `eval` 复用 `retrieval + llm`，保证调试页/问答页/评测"同一条检索代码路径"（对应 3.3 一致性要求）。
2. **MinerU 接入点**：`ingestion.parse.DocumentParser` 接口（输入：MinIO 对象流 + 文件类型；输出：统一
   `ParsedDocument{text, pages[{no, text}], structure hints}`）。第一版按扩展名路由 parser；MinerU 作为远端 HTTP
   服务的新实现注册进路由表即可，流水线阶段不变。
3. **BGE-Reranker 接入点**：`retrieval.Reranker` 接口（输入 query + 候选 hits，输出重排 hits）。第一版实现为
   `NoOpReranker`（恒等），第二/三轮替换实现，`RetrievalService` 骨架不动。
4. **模型切换点**：`config.RagProperties.Models` 驱动 LangChain4j client 构造，业务代码只依赖 LangChain4j 的
   `StreamingChatModel` / `EmbeddingModel` 接口，不依赖具体实现类。

## 3. 关键数据流

### 3.1 上传入库异步流水线

```text
POST /knowledge-bases/{kbId}/documents (multipart)
  1. 同步校验：KB 存在、扩展名/大小合法、(kb_id, content_sha256) 唯一约束命中 → 409 DUPLICATE_DOCUMENT
  2. 写 MinIO 源对象（ragsource/{kbId}/{docId}/source.pdf）成功后建 document + ingestion_task 行（status=QUEUED）
  3. 立即返回 202 {document, task}                          ← KB-3 不等待
  4. IngestionTaskManager 线程池认领：UPDATE ... SET status='RUNNING'
     WHERE id=? AND status='QUEUED'   ← CAS，天然防双跑，单实例下兜底
  5. 阶段推进：PARSING → CLEANING → CHUNKING → EMBEDDING → INDEXING → COMPLETED
     每阶段完成即更新 task.stage；产物落 MinIO/ES/MySQL
  6. 任一阶段异常 → status=FAILED，记 failure_stage + failure_reason（错误码枚举，含 SCANNED_PDF_NOT_SUPPORTED）
```

**幂等与去重（KB-8/KB-9）**：

- **文档级去重**：`document` 表 `UNIQUE(kb_id, content_sha256)`，sha256 在上传同步阶段计算（50MB 上限内开销可接受）。
- **阶段复用**：各阶段产物有确定性落点——解析文本 `parsed.txt`、分块在 ES（`doc_id` 定位）。重试从 `failure_stage`
  继续；已完成阶段按下述证据跳过，不重做：
  - PARSING 完成 ⇔ `parsed.txt` 对象存在（PutObject 成功即完成标志）；
  - CHUNKING/EMBEDDING/INDEXING 合并为"重建分块"语义：ES 先 `delete_by_query(doc_id)` 再 bulk 写入，
    天然幂等，重复执行不产生重复分块；
  - CLEANING 为纯内存变换，产物随解析文本落盘，无独立幂等问题。
- **中断恢复**：应用启动时把处于 QUEUED/RUNNING 的任务重新置为 QUEUED（RUNNING 记 attempt+1），
  由恢复逻辑按阶段证据续跑或失败。**前提是分块重建幂等**，因此不会出现"半批分块"残留。
- **任务表只保留当前任务**（attempt 计数 + failure 字段），第一版不做任务历史列表（列表页只需当前状态）。

### 3.2 问答链路（QA-1~6、QA-8）

```text
POST /qa/stream {kbId, sessionId, question, clientRequestId?}
  1. 校验 KB/Session；clientRequestId 若已在活跃流中 → 409 STREAM_ALREADY_ACTIVE（防重复提交）
  2. 持久化用户消息（立即落库 → QA-8 输入不丢）
  3. SSE 通道建立，发 stage: RETRIEVAL_STARTED
  4. RetrievalService：question 向量化（embedding 服务）→ ES kNN（filter: knowledge_base_id，size=topK，
     min_score 过滤）→ hits；发 stage: RETRIEVAL_COMPLETED {detail: "命中 N 块 · Xms"}
  5. ContextAssembler：hits 按分数拼接上下文（截断至 max-context-chars，记录是否截断）
  6. SessionService 取本会话最近 N 条历史仅作对话连贯性，注入 prompt 的"对话历史"区，与"文档证据"区严格分开
     （QA-3：历史不是证据；prompt 明示"仅依据文档证据回答，证据不足时明确说明，禁止编造引用"）
  7. StreamingChatModel 流式生成，逐 token 发 token 事件；发 citations 事件（= 本次实际检索 hits，
     含 chunkId/score，资料不足时为空数组 → QA-6 无伪造引用）
  8. 落库助手消息（content + citations + status），发 done 事件（终态）
  9. 超时（配置，默认 120s 无 token）/模型异常 → error 事件 MODEL_TIMEOUT / MODEL_UNAVAILABLE（终态），
     助手消息记 ERROR + failure code；客户端断连或 POST /qa/cancel → canceled 事件（终态），停止后续生成
```

SSE 事件契约语义（与 OpenAPI 一致）：`stage` / `token` / `citations` / `done` / `error` / `canceled` 六种；
顺序保证 `citations` 先于 `done`；`done`/`error`/`canceled` 互斥且为终态；**stage 枚举固定为真实发生的阶段，
禁止虚假进度百分比**（QA-4）。取消双通道：客户端主动 `POST /qa/cancel {clientRequestId}`，或直接断开 SSE
（服务端 onCompletion/onError/onTimeout 检测断连停止生成），两者最终都产生终态事件/落库。

### 3.3 删除与跨存储清理（KB-1/KB-9、业务规则 4）

```text
DELETE /documents/{docId} 或 DELETE /knowledge-bases/{kbId}?confirm=true
  1. MySQL 事务内：标记删除（文档行删除 / KB 级联删除文档、会话、消息）→ 检索边界立即收口
     （ES 查询按 doc_id/kb_id 命中已被删主档则视为无效；且清理任务秒级跟进）
  2. 为每个受影响对象写 cleanup_task 行（store=ELASTICSEARCH/MINIO，payload 含对象键/doc_id/kb_id），
     status=PENDING
  3. 返回 DeletionSummary（MySQL 侧统计 + cleanupTasksAccepted）← 明确"跨存储非原子"
  4. @Scheduled 每 30s 扫 PENDING/FAILED 的 cleanup_task：ES delete_by_query(doc_id|kb_id)、
     MinIO RemoveObjects；成功→DONE；失败→FAILED + last_error + attempts+1，下轮重试（无上限但记录）
```

可追踪性：清理失败留在 `cleanup_task` 表（attempts、last_error、updated_at），文档列表对"已删但清理未完成"
不做专门 UI（第一版），但 actuator 暴露 `rag.cleanup.pending/failed` 指标，日志含 task_id。

## 4. 持久化模型

### 4.1 MySQL 核心表（Flyway：`db/migration/V1__init.sql`，MySQL 8，utf8mb4）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `knowledge_base` | id CHAR(36) PK（UUID）、name UNIQUE、description、created_at、updated_at | 名称唯一与原型"重名被拒"一致 |
| `document` | id CHAR(36) PK、kb_id FK、name、file_type(PDF/MD/TXT)、size_bytes、content_sha256、status、current_stage、chunk_count、chunk_config JSON、source_object_key、parsed_object_key、failure_stage、failure_reason、created_at、updated_at | `UNIQUE(kb_id, content_sha256)` ← 去重约束；chunk_config 记录策略与参数（KB-6 可解释） |
| `ingestion_task` | id CHAR(36) PK、document_id UNIQUE FK、status(QUEUED/RUNNING/COMPLETED/FAILED)、stage、attempt、failure_stage、failure_reason、created_at、started_at、finished_at | 状态机唯一载体 |
| `cleanup_task` | id CHAR(36) PK、scope(DOCUMENT/KNOWLEDGE_BASE)、ref_id、store、payload JSON、status(PENDING/RUNNING/DONE/FAILED)、attempts、last_error、created_at、updated_at | 跨存储补偿记录 |
| `chat_session` | id CHAR(36) PK、kb_id FK、title、created_at、updated_at | 删 KB 级联删会话 |
| `chat_message` | id CHAR(36) PK、session_id FK、role(USER/ASSISTANT)、content MEDIUMTEXT、citations JSON、status(COMPLETED/ERROR/CANCELED)、error_code、created_at | citations JSON 存 Citation[]，与契约 schema 同构 |
| `eval_dataset` | id CHAR(36) PK、name UNIQUE、dataset_type(TUNING/TEST)、created_at | EV-6 类型标记 |
| `eval_dataset_version` | id CHAR(36) PK、dataset_id FK、version_no INT、item_count、source_name、created_at | EV-4 版本留痕；导入产生新版本，旧版本不可变 |
| `eval_dataset_item` | id CHAR(36) PK、version_id FK、seq、question、reference_answer、evidence JSON（EvidenceRef[]）、answerable BOOL、category(DIRECT/TERM_VARIATION/FOLLOW_UP/OUT_OF_KB/CONFUSABLE)、created_at | EV-1/EV-5 字段完整 |
| `eval_run` | id CHAR(36) PK、dataset_version_id FK、kb_id、status(RUNNING/COMPLETED/FAILED)、config_snapshot JSON（模型名/参数/topK/minScore/分块策略/向量维度）、metrics JSON（hitAt1/3/5、avgLatencyMs、itemCount）、failure_reason、started_at、finished_at | EV-4 快照保证两次运行可区分 |
| `eval_run_item` | id CHAR(36) PK、run_id FK、seq、question、retrieved JSON（rank/chunkId/docName/titlePath/page/score）、generated_answer、citations JSON、hit BOOL、latency_ms、review_tag NULL(OK/WRONG_ANSWER/MISSING_EVIDENCE/WRONG_SOURCE/OTHER)、review_note | EV-3；review 两列可空 = 未标注 |

**分块正文不进 MySQL**：chunk 全文唯一存于 ES（检索与预览同源，避免双写不一致）；MySQL 只存
`chunk_count` 等聚合。分块预览接口（`GET /documents/{docId}/chunks`）由后端查 ES 透出。

### 4.2 ES 索引设计

索引 `rag_chunks_v1`（别名 `rag_chunks`；v1 后缀为未来改 mapping/reindex 预留），应用启动时按当前
mapping 版本检查并创建：

```jsonc
{
  "mappings": {
    "properties": {
      "id":               { "type": "keyword" },            // chunkId = {docId}-c{seq,4位}（确定性，可重放）
      "doc_id":           { "type": "keyword" },
      "knowledge_base_id":{ "type": "keyword" },            // kNN filter term，QA-1 跨库隔离
      "title_path":       { "type": "keyword" },            // 展示用原始路径，不参与检索
      "page":             { "type": "integer" },            // PDF 有、MD/TXT 为 null
      "seq":              { "type": "integer" },
      "char_count":       { "type": "integer" },
      "content":          { "type": "text", "analyzer": "content_analyzer" },  // 为第二轮 BM25 预埋
      "vector":           { "type": "dense_vector", "dims": ${embedding.dimensions},
                            "index": true, "similarity": "cosine" }
    }
  }
}
```

- **中文分词**：`content_analyzer` 由 `rag.elasticsearch.content-analyzer` 配置，默认 **`ik_max_word`**
  （推荐部署 `analysis-ik` 插件的 ES 8 镜像；第二轮 BM25 混合检索直接受益）。应用创建索引前探测分析器
  可用性，不可用则启动失败并提示两个选项：安装 IK，或改配 `standard`（标准分词对中文只做逐字/弱切分，
  BM25 召回质量差，但第一版纯向量检索不受影响——这是明确记录的取舍，不是隐性降级）。
- kNN 查询：`knn { field: vector, query_vector, k: topK, num_candidates: max(100, 10*topK),
  filter: [{term: knowledge_base_id}] }`，配合 `min_score` 在应用侧过滤（ES kNN 的 min_score 语义经实测
  确认后再决定下推与否，第一版应用侧过滤行为可解释）。

### 4.3 MinIO 对象键规范

桶 `rag-data`（可配置）：

```text
ragsource/{kbId}/{docId}/source.{pdf|md|txt}   原始上传文件（原样字节）
ragsource/{kbId}/{docId}/parsed.txt            解析+清洗产物（PARSING 完成标志，重试跳过依据）
```

键只由 UUID 组成，**用户文件名永不进入对象键**（规避路径注入/非法字符）；删除按 `{kbId}/{docId}/` 前缀
列举后批量删。KB 删除按 `ragsource/{kbId}/` 前缀清理。

## 5. 模型服务配置（application.yaml）

```yaml
rag:
  models:
    startup-check: true          # 启动时向 embedding 服务发一次探活请求，失败即拒绝启动并给出明确提示
    chat:
      base-url: ${CHAT_MODEL_BASE_URL}          # 必填，OpenAI 兼容端点，如 http://localhost:8000/v1
      api-key:  ${CHAT_MODEL_API_KEY:}          # 可空（本地推理服务常不需要），绝不写入仓库
      model-name: ${CHAT_MODEL_NAME:qwen2.5-7b-instruct}
      temperature: 0.2
      timeout-seconds: 120                       # 首 token 前与 token 间 idle 超时共用
      max-history-messages: 8                    # QA-3 会话历史注入上限（仅连贯性，非证据）
    embedding:
      base-url: ${EMBEDDING_BASE_URL}
      api-key:  ${EMBEDDING_API_KEY:}
      model-name: ${EMBEDDING_MODEL_NAME:bge-m3}
      dimensions: 1024                           # 必须与模型实际输出一致；startup-check 时校验
      timeout-seconds: 30
  retrieval:
    top-k: 6
    min-score: 0.30
    max-context-chars: 6000
  ingestion:
    worker-threads: 2
    max-upload-size-mb: 50
  elasticsearch:
    content-analyzer: ik_max_word
spring:
  threads.virtual.enabled: true
  servlet:
    multipart:
      max-file-size: 50MB
      max-request-size: 55MB
```

- `RagProperties` 用 `@Validated` + jakarta 注解做静态校验（base-url 缺失、dimensions≤0、top-k<1 等启动即报）；
- `startup-check=true` 时额外做一次真实 embedding 调用：验证连通性 + 实际返回维度与配置一致（不一致是
  最隐蔽的线上事故源，必须启动期拦截），失败信息直接指出哪个变量没配对。关闭开关仅用于模型服务晚于应用启动的本地场景；
- API key 只从环境变量/启动参数读取，`application.yaml` 示例文件不含真实密钥（需求 §7）。

## 6. SSE 事件契约语义（摘要，详见 openapi.yaml）

| 事件 | data 要点 | 终态 |
| --- | --- | --- |
| `stage` | `{stage: RETRIEVAL_STARTED \| RETRIEVAL_COMPLETED \| GENERATION_STARTED, detail?, elapsedMs?}` | 否 |
| `token` | `{delta: string}` 增量文本 | 否 |
| `citations` | `{citations: Citation[]}` 恰好一次，生成完成后发送；内容=本次实际检索 hits | 否 |
| `done` | `{messageId, elapsedMs}` | 是 |
| `error` | `{error: {code, message, requestId}}`，code ∈ MODEL_TIMEOUT/MODEL_UNAVAILABLE/RETRIEVAL_FAILED/STREAM_INTERRUPTED/INTERNAL_ERROR | 是 |
| `canceled` | `{reason: "USER_CANCELED"}` | 是 |

传输格式：标准 `text/event-stream`，每个事件 `event: <类型>` + `data: <JSON>`；心跳注释行 `:ping` 每 15s。
OpenAPI 以 `responses['200'].content['text/event-stream']` + `QAStreamEvent` oneOf 组件描述载荷结构。

## 7. 鉴权与安全边界

- **无登录是需求**（§4 非目标），不是遗漏。部署假设：**本机/可信内网单用户**。契约预留
  `components.securitySchemes`（注释态），第一版所有 path 不挂 `security`。
- **密钥只走环境变量**（见第 5 节）；日志脱敏：api-key、Authorization 头永不打印。
- **上传校验**：扩展名白名单（pdf/md/txt）+ 大小上限（50MB）+ magic bytes 粗校验（%PDF / 文本 UTF-8 可解码）；
  扫描件在 PARSING 阶段检测（首页无文本层 → FAILED/SCANNED_PDF_NOT_SUPPORTED）。
- **SSRF/路径约束**：模型 base-url、ES、MinIO 地址全部来自服务端配置，用户请求永远不提供任何后端将访问的
  URL/主机/桶/索引名；对象键仅 UUID（见 4.3）；文档名仅作展示字段存取，不参与文件系统或对象键拼接。
- **SSE**：响应头 `X-Accel-Buffering: no`（防代理缓冲）；单连接写超时由 SseEmitter timeout 兜底。
- CORS：第一版前后端同源部署（Next.js 代理 `/api` 到后端），仅开放本地 dev origin。

## 8. 错误处理与可观测性

- **统一错误体** `Error{code, message, requestId, details?}`，HTTP 状态与 code 的映射集中在
  `api/GlobalExceptionHandler`；稳定 code 枚举见契约 `Error` schema 描述（KB_NOT_FOUND、
  DUPLICATE_DOCUMENT、UNSUPPORTED_FILE_TYPE、SCANNED_PDF_NOT_SUPPORTED、MODEL_TIMEOUT、
  STREAM_ALREADY_ACTIVE、CONFIRMATION_REQUIRED 等 24 个）。
- **requestId**：`OncePerRequestFilter` 生成/透传 `X-Request-Id`，进 MDC，出现在所有日志行与错误体。
- **任务失败原因落库**：ingestion_task.failure_reason 存错误码枚举 + 人读文案；eval_run.failure_reason 同理。
- **日志规范**：流水线与问答链路每行日志携带 `taskId` 或 `docId`/`sessionId`+`clientRequestId`（MDC）；
  级别规则：外部服务失败=WARN+堆栈、业务去重/取消=INFO、未知异常=ERROR。
- **Actuator**：`health`（含 db/es/minio/ragModels 分项）、`info`、`metrics`（含自定义
  `rag.ingestion.tasks{status}`、`rag.cleanup.pending`、`rag.retrieval.latency`）；仅内网可访问。

## 10. 重要取舍与替代方案

1. **ES 而非 PGVector/Milvus**（用户已锁定，架构上也自洽）：分块正文、来源元数据、向量同仓，kNN filter
   原生支持 kb 隔离；第二轮 BM25+RRF 混合检索零迁移。代价：ES 运维重于单机 PG；部署文档需给 docker-compose。
2. **进程内线程池 + DB 任务表，而非消息队列**：第一版单实例、任务量（个人/小团队文档库）在百~千级，
   MQ 的运维成本与语义（至少一次、重试拓扑）收益不成立。代价与边界：**多实例不能共用此机制**（CAS 认领防
   双跑但仍需实例间协调），扩容前必须先换队列；代码上把 `IngestionTaskManager` 的"取任务"收敛为单一接口，
   升级路径 = 换实现，流水线阶段不动。启动恢复（QUEUED/RUNNING 复位）替代了 broker 的未决消息语义。
3. **分块正文只存 ES**：单写单读，无双写一致性负担；代价是 MySQL 侧没有分块级审计副本，可接受。
4. **Spring MVC + 虚拟线程，而非 WebFlux**：SSE 场景下阻塞式代码 + 虚拟线程足够，可读性/调试成本远低于响应式。
5. **扫描件异步检测而非上传同步检测**：同步预检需在上传线程解析 PDF 样本，大文件拖慢受理且不可靠（部分 PDF
   前 N 页无文本但后文有）；异步失败 + 明确错误码 + 行内提示已满足 KB-2"明确提示而非静默失败"。
6. **SSE 而非 WebSocket**：单向推送、HTTP 语义、经代理更稳，契约可直接用 OpenAPI 描述。

## 11. 实现约束与非目标（第一版明确不做）

- 不做登录/多租户/RBAC/计费；不做多实例与分布式协调；不引 Redis/MQ。
- 不做 BM25/RRF/BGE 重排、意图识别、查询改写（接口位已留）。
- 不做 Word/Excel/CSV 解析、扫描件解析、文档多版本、MinerU 接入（仅留接口）。
- 不做完整评测管理 UI（评测只有 API + 最小可用调试能力；前端导航不放评测入口，与原型一致）。
- 不做文档级进度推送（WebSocket/SSE 任务进度）；任务进度 = 前端轮询 `GET /documents/{docId}/task`。
- 不做跨存储强一致承诺（补偿表兜底）；不做分块正文的 MySQL 副本。
- 运行环境约束：不假设本机 GPU；模型服务为外部 HTTP（OpenAI 兼容）；ES 镜像建议含 IK 插件，否则降级
  standard（第 4.2 节）。

## 12. 已确认的契约语义决策（随本路线一并审批）

以下点曾存在多种合理设计，本文与契约采用如下取值；如你希望不同取值，请在批准时指出：

1. **扫描件检测时机 = 异步**：上传正常受理（202），解析阶段检出后任务失败并显示
   SCANNED_PDF_NOT_SUPPORTED；前端文档列表行很快出现失败原因与重试入口（满足 KB-2"明确提示"）。
   原型中"上传弹窗内立即提示"属演示简化，以前端识别扩展名+提示实现为体验层辅助，最终判定以后端为准。
2. **删除知识库级联删除其下会话与消息**（DeletionSummary 给出计数），与原型确认文案一致。
3. **`POST /qa/stream` 的 sessionId 必填**：提问前须有会话；前端在无会话时自动创建（UI 上无感知）。
4. **多轮追问检索局限**：第一版检索仅用当前问题向量化（不做改写/独立化），"那第二个方案呢"类指代追问
   召回差是预期行为，验收时列为已知局限而非缺陷（第二轮优化项）。
5. **Embedding 模型/维度变更需清库重建**：第一版无向量索引迁移工具，记为运维约束。
6. **Hit@K 语义**：以该次运行的 topK 为 K，摘要输出 Hit@1/3/5；样本级 hit 字段同步保存。
7. **评测样本第一版只支持"导入新版本"**，不支持逐条编辑（完整管理 UI 本就在第二轮）。
