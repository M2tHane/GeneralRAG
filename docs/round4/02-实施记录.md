# R4 实施记录：Evidence Answerability

> 撰写时间：2026-09-15。第四轮「让系统知道自己什么时候有答案」全量实施与对照评测记录。
> 前置分析见 `docs/round4/01-Baseline分析.md`。

## 1. 一句话结论

在 72 题 Answerability 专项集上，新策略把 **False Answer Rate 从 47.4% 降到 10.5%**（FP 18→4），
代价是 False Refusal Rate 0%→5.9%（FN 0→2），检索指标（Hit@K/MRR/Recall）零变化，
Judge 调用率 72.2%、平均耗时 2.57s、降级率 0%。

## 2. 最终架构

```text
Retrieval（RetrievalPipeline，未动）
    ↓
ContextAssembler（未动）── 产物 Context.text 同时喂 ↓ 和生成 Prompt（同源，防证据漂移）
    ↓
AnswerabilityPolicy（新增，Chat/Debug/Eval 共享单实例）
    1. enabled=false → ANSWERABILITY_DISABLED（旧 RefusalPolicy 行为，对照用）
    2. hits 为空 → NO_HITS
    3. topScore < lowThreshold（rerank 0.65 / cosine 0.30，沿用 R2 双口径校准）
       → LOW_SCORE_REFUSAL（不调 Judge）
    4. 其余全部 → EvidenceSufficiencyJudge（temperature=0 阻塞调用 + Future 超时）
       成功 → JUDGE_ACCEPT / JUDGE_REFUSE
       失败 → JUDGE_DEGRADED：failClosed=false 退回旧阈值行为放行（显式标注）；
              failClosed=true 保守拒答
    ↓
answerable=true → PromptAssembler → StreamingChatModel（判定的 confidence/reason 不进 Prompt）
answerable=false → 固定拒答文案 token 流 + citations=[]
```

**为什么不设 highThreshold 直答**：Baseline 实测 PARTIAL_EVIDENCE 与可答题的 rerank
分布完全重叠（两类都有 1.000，见 01-Baseline §3），任何高分直答都会漏 FP——原候选
方案被自己的数据否定，改为"低分硬拒 + 其余全 Judge"。

**Judge 失败为什么退回旧阈值而不是保守拒答**：灰区 52 题若全拒，FRR=100%（34 可答全灭）；
全放行=回到 FAR 35% 旧态。"退回旧策略"误判上界=旧系统本身，且 JUDGE_DEGRADED
在 Eval/Debug/日志三处可观测。`fail-closed=true` 保留给高风险部署场景。

## 3. 阈值来源（全部有数据出处）

| 阈值 | 值 | 依据 |
| --- | --- | --- |
| lowThreshold（rerank 口径） | 0.65 | R2 调优集校准（可答 ≥0.787 / 资料外 ≤0.630）；Baseline 72 题上可答 min=0.747，0.65 留 0.097 安全带 |
| lowThreshold（cosine 口径） | 0.30 | R2 校准；余弦口径区分度弱，只能过滤明显不相关（Baseline 复测：可答 min=0.774，不可答 min=0.633，重叠） |
| highThreshold | 不存在 | 不可答 max=1.000 与可答满分重合，无安全值（01-Baseline §3 阈值扫描表） |
| judgeTimeoutSeconds | 15 | chat timeout 120s 的 1/8；Judge 只需输出短 JSON，实测 avg 2.57s |
| maxEvidenceChars | 4000 | 与生成上下文同源截取（max-context-chars 6000 内已含），控制 token 成本 |

## 7. 残留 FP / FN 逐题

### 残留 FP（4，全部 PARTIAL_EVIDENCE，全部 JUDGE_ACCEPT conf≥0.95）

| seq | rerank | Judge 认知 | 数据集预期 | 归因 |
| -- | -- | -- | -- | -- |
| 56 | 1.000 | "四原因+处理手段完整覆盖" | 处理手段未与原因一一对应 | **判定语义分歧**：Judge 认为通用措施覆盖各原因即可；数据集要求逐项对应。边界题，两种口径都站得住 |
| 59 | 1.000 | "三类错误码处置完整" | 生产端仅 1 条且跨 Row-group 分块 | 数据集过严——语料其实覆盖了三类各至少 1 条 |
| 60 | 1.000 | "核心数×2 依据已写明" | 依据细节未解释 | **判定语义分歧**：语料确实写了"核心数×2，DB CPU 占用可忽略" |
| 63 | 0.976 | "busy_buffers 默认=两块大小已给出" | "怎么计算"的规则细节没有 | **判定语义分歧**：默认值可视为可答 |

**发现**：残留 4 题中 3 题（56/59/60）是数据集预期过严或判定口径边界，而非 Judge 幻觉。
真正"该拦没拦"的边界题约 1 题（63）。**这批题必须重新人工核对预期标签**——
这正是 Bad Case 驱动迭代的下一步：修数据集而不是调系统。

## 8. 性能成本

- Judge 调用率 72.2%（52/72）：低分题 27% 零额外成本
- Judge 平均 2570ms（P95 约 4s）；E2E 增量 +944ms/题（拒答题省下生成时间部分抵消）
- Judge 降级率 0%（本环境模型服务稳定）

## 9. 当前限制（如实声明）

1. **Judge 自身会误判**：残留 FP 的 4 题里 Judge 全部给出 conf≥0.95 的高置信错误——置信度不能当真值用；
2. **数据集预期标签需要人工复核**：PARTIAL_EVIDENCE 的"完整回答"边界（通用措施算不算覆盖逐项问题）存在口径争议，本轮已识别 3 题；
3. Follow-up 仍无 query rewrite（判定不受影响，但检索本身对指代题弱——本轮 6 道 FOLLOW_UP 有 5 道 TP）；
4. Judge 与生成共用同一模型（本地部署单模型约束）；换独立小模型是后续优化点；
5. E2E 延迟 +33.7%，对延迟敏感场景可 `RAG_ANSWERABILITY_ENABLED=false` 快速回退。

## 10. 下一轮建议（严格按本轮 Bad Case）

1. **复核 PARTIAL_EVIDENCE 标签口径**（4 题残留 FP 全在此类）——先修数据集，再谈系统；
2. **不需要** Query Rewrite / Parent-Child / Metadata Filter / GraphRAG：本轮 72 题 Bad Case
   全部发生在"检索正确、判定/生成"层，Hit@3=1.0 说明召回与排序不是瓶颈；
3. 唯一检索侧观察：CONFUSABLE(true) 6 题全对、误判集中在判定层——若后续扩大语料后
   Hit@1 下降，再考虑查询改写。
