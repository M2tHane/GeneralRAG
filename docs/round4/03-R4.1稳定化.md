# R4.1 实施记录：Answerability 工程稳定化

> 撰写时间：2026-09-16。本轮（R4.1 Answerability Stabilization）目标是把 R4 的
> Answerability 方案从"实验上有效"提升到"工程上可信"——**不新增任何 RAG 能力**。
> 前置：R4 记录见 `docs/round4/02-实施记录.md`。

## 1. 本轮修复的问题

| # | 问题 | R4 现状 | R4.1 修复 |
| --- | --- | --- | --- |
| 1 | Judge 单线程瓶颈 | `Executors.newSingleThreadExecutor` + `Future.get(15s)`，并发请求全部串行排队，排队时间计入 15s 超时 | Semaphore bulkhead（`max-concurrent-judges`，默认 4）+ 调用线程同步执行；容量耗尽按 OVERLOADED 快速降级，不无限排队 |
| 2 | Timeout 语义失配 | Future 15s vs HTTP 120s：上层已放弃、底层请求继续跑（假取消） | `judge-timeout-seconds` 直接作为 judgeChatModel 的 HTTP connect/read timeout；langchain4j 同步调用在 read timeout 处硬中断（已验证），且 `maxRetries=0` 关闭重试——超时值 = 单次判定真实上界 |
| 3 | Evidence 不一致 | `ContextAssembler` 6000 字 vs Judge `substring(0,4000)`：Judge 可能看不到 4000~6000 区间的答案，且按字符中间截断分块 | 删除 `max-evidence-chars`；Judge 收到与生成**同一个 Context 实例**的全文；分块级截断只发生在 ContextAssembler（整块丢弃，不切半块） |
| 4 | 重复 assemble | 流式路径 `assemble(passed)` 调用 2 次、eval 路径 1 次但语义分散 | 单次 assemble；`AnswerabilityPolicy.evaluate(AnswerabilityInput)` 接收 Context 对象 |
| 5 | 无 Answerability E2E 测试 | QaStreamIT 显式关闭 answerability | 新增 `AnswerabilityFlowIT`（7 场景，见 §5） |
| 6 | OpenAPI 契约漂移 | Java 已删 `HIGH_CONFIDENCE_ACCEPT`，契约未删 | 契约/前端 schema 同步删除；V4 迁移注释保留（immutable），未采用原因记录于本文档 §2 |
| 7 | FOLLOW_UP 评测名不副实 | `answerOnce(..., List.of())`——history 恒空，却按 follow-up 能力解释 | V5 迁移 + 解析/执行/契约全链路支持数据集级 history；6 道 FOLLOW_UP 题补齐指代上下文 |
| 8 | 标签口径无指南 | PARTIAL_EVIDENCE 边界靠临时裁定 | 新增 `docs/eval/answerability-labeling-guide.md`（§6） |

## 2. Judge 新并发架构（before / after）

```text
R4（before）：
SSE/eval 线程 → AnswerabilityPolicy → judgeExecutor.submit(单线程池)
                                          └─ Future.get(15s)  ← 排队时间计入超时
                                          └─ 底层 HTTP timeout 120s ← 与上层失配
                                          └─ 任务完成后线程池复用（假取消：Future 超时
                                             后底层 HTTP 仍在跑）

R4.1（after）：
SSE/eval 线程 → AnswerabilityPolicy → Semaphore bulkhead（permits=4）
                                          ├─ tryAcquire(500ms) 失败 → OVERLOADED 快速降级
                                          └─ 获得名额 → 同步 judgeModel.chat()
                                                ├─ HTTP connect/read timeout = judge-timeout-seconds
                                                ├─ maxRetries=0（超时=单次尝试上界）
                                                └─ 异常链含 HttpTimeoutException → 归类 TIMEOUT
                                                finally: bulkhead.release()（成功/失败/中断都释放）
```

并发语义验证（单测 `concurrentJudgesRunInParallel` / `bulkheadExhaustionFailsFastWithOverloaded`）：
- 4 并发 × 300ms mock 模型：同时活跃数 ≥2 观测到，总耗时 ≈单次而非 4 倍——真实并发；
- 2 permits 全占 + 第 3 请求：快速失败 OVERLOADED（<1s），且不打扰模型。

**默认值 `max-concurrent-judges=4` 的依据**（非拍脑袋）：
- SSE 并发上限 32（AsyncConfig），评测串行（单线程 executor）；
- 判定实测 avg ≈ 2.6s：4 路并发下 32 并发流的排队期望 ≈ 8×2.6/4 ≈ 5.2s，仍在
  timeout 量级内、可用性优先；
- 本地单实例模型（Judge 与生成共用 deepseek-v4-flash）吞吐随并发恶化，
  4 是"不把模型打满"与"不长时间排队"的折中；2/8 语义已由配置支持，
  并发冒烟（§9）可按部署环境实测后调整。

## 3. Timeout 语义（各层明确）

| 层 | 参数 | 含义 |
| --- | --- | --- |
| 连接 | judge-timeout-seconds（HTTP connect） | 与模型端点建立 TCP 连接的上界 |
| HTTP/模型 | judge-timeout-seconds（HTTP read） | 单次判定请求从发出到响应完成的上界；到点底层硬中断（HttpTimeoutException），**不存在后台孤儿请求** |
| bulkhead 等待 | bulkhead-wait-ms（默认 500ms） | 等待并发名额的上界；耗尽 → JUDGE_DEGRADED(OVERLOADED) |

失败原因四分类（`JudgeUnavailableException` message 前缀，Debug/Eval 落库的
`answerabilityReason` 与日志可见）：`TIMEOUT` / `OVERLOADED` / `MODEL_ERROR` /
`INVALID_RESPONSE`。旧 Future 超时与模型超时混为一谈的问题消除。

## 4. Evidence 一致性

- **同一个 Context 实例**：`runStream`/`answerOnce`/`debug` 均 assemble 一次，
  `AnswerabilityInput.context` 与 `promptAssembler.build(..., context)` 指向同一对象；
- **全文进 Judge**：`max-evidence-chars` 删除，Judge 提示词的证据区 = `Context.text()`
  原文（最多 6000 字，由 max-context-chars 控制）——单测
  `evidencePassedInFullWithoutMidChunkTruncation` 钉死（6000 字跨"两个分块"内容完整可见）；
- **按整块截断**：长上下文时 ContextAssembler 丢弃放不下的整个分块（R4 前行为保留），
  不再出现"Judge 视角把某块切一半"的中间态；
- **Judge↔生成隔离不变**：判定 confidence/reason 不进生成 Prompt；
  R4.1 新增：Judge 可见对话历史，但提示词明确"对话历史仅用于理解当前问题中的指代，
  不能作为知识事实依据"（单测 `historyGoesIntoPromptWithNonEvidenceDisclaimer` 钉死）。

## 5. Integration Test（AnswerabilityFlowIT，7/7 通过）

Testcontainers（MySQL/MinIO/ES）+ FakeOpenAiServer，answerability **开启**（与
QaStreamIT 互补），VECTOR 模式。覆盖：

| Case | 场景 | 关键断言 |
| --- | --- | --- |
| 1 | Judge Accept | 完整 stage 序列含 ANSWERABILITY_CHECKED（"可回答"）→ 生成 → citations 非空 → done；非流式请求数=1 |
| 2 | Judge Refuse | 判定"证据不足" → 拒答文案 token → citations=[] → done；**Judge 1 次、生成模型 0 次** |
| 3 | Malformed JSON | JUDGE_DEGRADED → 按默认 failClosed=false 退回旧阈值放行 → 生成照常 |
| 4 | Judge Timeout | 6s 慢响应 + 2s HTTP timeout → ~2s 处硬取消（总耗时 <9s 上限）→ 降级放行；**后续 Judge 正常工作（bulkhead 名额已释放）** |
| 5 | 低分直拒 | 不调 Judge（非流式请求数=0）、不调生成；拒答文案 + citations=[] |
| 6 | SSE 契约 | stage 名次序 RETRIEVAL_STARTED → RETRIEVAL_COMPLETED → ANSWERABILITY_CHECKED → GENERATION_STARTED；token 全部在 stage 后；citations 恰一次在 done 前；Judge 提示词含与生成同源的证据全文与当前问题 |
| 7 | 准备 | KB/会话/文档/索引（@Order(1)） |

测试基建修复：FakeOpenAiServer 的流式响应缺 `\n\n` 分隔符（严格 SSE 客户端把
多个 data 行合并为一个事件——此前仅靠宽松解析未暴露）；新增 Judge 定向控制
（非流式专用 answer/delay/500/计数/并发峰值）。

**如实说明（IT 内记录）**：fake 向量含公共基分量使 ES knn score=(1+cos)/2 恒 >0.5，
默认 cosine 阈值 0.30 在该环境永远无法触发低分直拒——FlowIT 显式设 0.90 区分高低分。
生产环境分数分布由真实模型决定，不受此影响。

**拒答路径的事件序列**：按 R4 已发布契约，拒答路径同样发 GENERATION_STARTED
（R4 用户验收过该序列；需求 §八 亦注明"按当前契约为准"）。本轮不改此行为。

## 7. FOLLOW_UP 新语义

- **数据结构**：`eval_dataset_item.history`（V5 迁移，JSON NULL）= `[{role, content}]`
  时间正序；导入解析器校验 role ∈ {user, assistant}、content 非空；缺省 = 无历史；
- **执行**：`EvalRunExecutor.toHistoryTurns` 把样本 history 传给 `answerOnce` ——
  与问答链路 `loadHistory` 等价，评测终于真正测 follow-up 语义；
- **边界（未偷跑）**：检索仍只用当前问题（本系统无 query rewrite——评测测的是当前
  真实系统，不为 FOLLOW_UP 通过而拼 history 进检索）；history 只进生成 Prompt 历史区
  与 Judge 指代解析区，两处均声明"不构成回答依据/证据"；
- v1 数据集 6 道 FOLLOW_UP 的 history 已按语料上下文构造（v2 内）。
