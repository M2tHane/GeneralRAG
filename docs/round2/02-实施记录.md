## 1. 一句话结论

**第二轮最重要的产出不是"加了混合检索"，而是让评测能说真话。** 第一轮的 Hit@K=1.00 是文档级判定导致的指标退化（证据 titlePath 从未匹配真实分块路径，命中全靠 docName），在本轮修复为分块级判定后，同一语料上首次出现了有区分度的基线：VECTOR Hit@1=0.50，HYBRID_RERANK Hit@1=1.00。

## 4. 过程中发现并修复的问题

1. **重排服务不是 OpenAI 兼容端点**（实测 `/compatible-mode/v1/rerank` → 404，原生端点 → 200）→ 单独配置块 + 原生 HTTP 适配。
2. **ES 原生 RRF 不可用**（license=basic → `retriever.rrf` 403）→ 融合改应用侧实现（附带收益：可单测）。
3. **融合分不能直接比 minScore**：原始 RRF 分 ~0.016；即使归一化，单通道召回的候选天然只有双通道的一半（0.5），会把相关命中系统性误拒。→ 融合分只用于**排序**，阈值/拒答用绝对余弦分（重排生效时用重排分）。
4. **拒答不能只有一套阈值**：实测余弦分无法区分资料外（0.65~0.77 与可答题区间重叠），重排分可以（可以 0.787~1.000 vs 资料外 0.142~0.630）→ 双阈值口径 + 单元测试守护"不得混用"。
5. **`toSummary` 硬编码旧指标**：新增的 Recall@5/MRR/拒答正确率无法到达列表页 → 改为透出 `metrics` 与 `configSnapshot`。
6. **前端 SSE error 载荷解析错位**（第一轮遗留）：后端发 `{error:{...}}`，前端按未包装类型读 → 模型失败时给用户显示 `undefined`。本轮修正并兼容两种形状。
7. **拒答文案与后端事实不符**（本轮走查发现）：前端显示「未从知识库召回相关资料」，但拒答场景实际是"有命中但证据不足" → 改为「本次未采用任何引用」并说明可去调试页查看。
8. **`QaStreamIT.clientDisconnectPersistsCanceledMessage` 是既有的间歇性失败**：日志证明失败时 `citations` 探测写入成功、消息已落库 COMPLETED，仅 `done` 写入失败——响应体仅 ~345 字节，被 Socket 缓冲吸收，服务端感知不到断连。已改为产生超缓冲输出以确定性触发设计路径（`终态事件发送失败 → handleDisconnectAfterTerminal → CANCELED`），连续 3+3 次运行稳定通过。

## 5. 未验证 / 已知缺口

- **查询改写未做**（按需求 §4 属 Later）：本轮全部样本仅 1 道 FOLLOW_UP 题证据偏弱，缺少 BadCase 群体支持；待真实 BadCase 集形成后再决定。
- **数据集 evidence 锚点的文件名耦合**：第二轮锚点用真实 `titlePath`（根为上传文件名），文档改名会使锚点失效；未引入更稳定的内容哈希键（成本更高）。第一轮格式数据集（docName 锚定）在新判定下会大量判为未命中——这是刻意的：它暴露"锚点不足"，而不是继续给虚假满分。
- **存量语料需重新入库**：R2-T1 修复只对重新入库生效；第一轮评测知识库（`a335d1f1…`）的分块仍是旧路径。重入库受 `UNIQUE(kb_id, content_sha256)` 限制，需先删文档（会连带使旧 chunkId 悬空）。
- **重排质量本身不做断言**：只能由评测运行体现；本报告给出的是实测数值，不是质量保证。
- **余弦口径的拒答正确率不可靠**（数据限制，非实现缺陷）：`VECTOR`/降级场景的拒答指标不能代表系统能力。
- 冷启动会显著抬高单题耗时（首调 embed 实测可达数秒 vs 稳态 ~0.17s），报告中的分位数含此影响。
- 未做键盘可达性逐项实操与 console error 采集。
