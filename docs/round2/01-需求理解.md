# 01 需求理解 — 第二轮：检索与效果优化

> 前置基线：`docs/01-需求理解.md`（第一轮，已批准，本文不修改它）、`docs/03-技术路线.md`、`prototype/DESIGN.md`（已批准 UX）、`docs/HANDOFF.md`。
> 本文为第二轮需求基线，需用户批准后方可进入 Stage 2/3。
> 第一轮已收口（109/109 测试绿、真实模型评测基线、E2E 通过）；本轮为路线图 §8 的第二轮范围立项。

## 0. 本轮的起点判断

HANDOFF 把第二轮定义为「BM25+向量 RRF → 重排 → 对比页 → 按 BadCase 决定查询改写」。启动调研后，两个独立视角（用户视角 / 开发视角）+ 主 Agent 独立复核 + 一次独立需求评审共同指向一个**必须先处理的前提问题**：

> **第一轮的 Hit@K=1.00 不是「检索很强」，而是「指标退化」。在修好度量之前做检索改造，无法被诚实评价。**

因此 MVP 的第一优先级不是加检索能力，而是**让评测说真话**。否则 BM25/RRF/重排的任何改动都会呈现为「指标无变化」，对比页只会把「无区分度」显示成「已验证无提升」。

### 0.1 对已批准路线图的偏离声明（需用户确认）

`docs/01-需求理解.md:103` 把**「八项指标（Hit@K、Recall@K、MRR、上下文 P/R、忠实性、正确性、相关性，LLM 裁判保留人工抽查）」明确列入第二轮**。本轮把其中「检索类指标」（Recall@K、MRR、排名分布）保留在 MVP，而把**「生成类指标」（忠实性/正确性/相关性 + LLM 裁判）移入 Later**（§4）。

**这是对已批准路线图的偏离，理由**：LLM 裁判需要裁判模型、成本机制与人工抽查流程，与检索内核改造混在同一轮会导致「说不清哪一步带来变化」；先稳定检索侧度量，再叠加生成侧裁判，才能保持归因清晰。

**请在批准本文时确认此偏离，或不认可并把它放回 MVP。**

## 2. 用户问题（本轮要解决什么）

1. **无法判断「哪种检索配置更好」。** 现有指标在文档级饱和，用户拿不到可信的对比结论——这是最核心的问题。
2. **技术文档问答的精确术语检索弱。** 向量检索对 `proxy_buffer_size` vs `proxy_buffers`、`appendfsync everysec`、错误码一类稀有 token 不敏感；这是该业务场景的高频真实诉求（BM25 通道的价值点）。
3. **引用条与分块预览出现「1.6. 6.」** 这类重复编号，显得系统不可信；且它同时让「按 titlePath 锚定证据」这条路径整体失效。
4. **拒答与引用自相矛盾。** 模型正确说「资料不足」，下面却挂 6 条来源。
5. **单题耗时长且不可归因。** 长对比题 22s，用户不知道慢在检索还是生成（实测检索侧 embed≈0.1s + kNN≈10ms，22s 属模型侧生成）。

## 4. Later（本轮不做，记录方向）

- **查询改写 / 多轮指代独立化**：当前全部样本中仅 1 道题（FOLLOW_UP）证据偏弱——**没有 BadCase 群体支持无条件引入一次模型调用**。待 R2-E 修复后产生真实 BadCase 集，再据此决定。

## 6. 业务规则与边界

1. **调优集只用于校准，测试集只用于结论**；不得用测试集反复调参后宣称泛化提升（沿用第一轮规则 5）。
2. **量化结论必须注明语料规模、题量、指标定义**；饱和指标上的 0 变化只能表述为「该指标无区分度」。
3. **外部依赖失败必须显式降级并留痕**：重排失败回退融合顺序，调试页/评测运行标注降级原因；禁止静默返回更差排序并计入对比。
4. **跨存储非原子、补偿可重试**（沿用第一轮）；引用语义变更不得破坏 `citations` 先于 `done` 的 SSE 顺序保证。
5. **两次评测运行是「可比」而非「逐位可复现」**：embedding 存在浮点微差、HNSW 为近似检索、候选集可能变动；报告须如实说明。
6. **`score` 语义不得静默改变**：若最终排序分不再是 cosine，必须显式更新契约描述并走 Stage 3 批准门（§7.3）；**且已落库的历史数据（`chat_message.citations`、`eval_run_item.citations/retrieved`）仍是旧语义，需在 §7.3 明确如何区分**。
7. 密钥只走环境变量，不入仓库（沿用第一轮）。
8. **已知代价（本轮如实记录，不宣称优化）**：重排上线后检索侧耗时从稳态 ≈0.2s 上升到 ≈0.6~1s 量级（候选 50 篇实测 0.51s；现有 kNN 候选窗口 `max(100, 10*topK)` 偏大，需按 §7.2 收敛）。

## 7. 留给 Stage 3 的技术语义决策（本轮不在此定稿，但需在 Stage 3 明确并获批）

1. **分块级锚点键（阻塞 R2-E1/R2-T2）。** 可用锚点均有耦合：`titlePath` 根为**上传文件名**（`StructureChunker.java:81`），改名即失效；`docId` 为随机 UUID；`chunkId = {docId}-c%04d` 随 docId 变；ES 分块**无内容哈希字段**。
   实测**否决**「用 evidence `snippet` 片段匹配」：16 条 evidence 中仅 7 条片段能命中真实分块正文（9 条因省略号/换行/格式差异不匹配）。
   **建议锚点 = 精确 `titlePath`（含 docName 前缀），evidence 按真实分块器输出重写（R2-E4），接受文件名耦合**；若需脱离文件名，则须新增稳定键（内容哈希或标题结构键），成本更高。**请用户在 Stage 3 前确认取舍。**
2. **融合与候选参数。** RRF `k` 取值；两通道候选数（现有 kNN 用 `max(100, 10*topK)`，对重排偏大，需收敛到约 30~50）；`minScore` 作用对象（向量分 / 融合分 / 重排分——三者量纲不同，`k=60` 时融合分约 0.009~0.033 而现默认 0.30，两者必有一个要动）。
3. **`score` 的含义与历史数据。** 建议 `score` = 最终排序分，另加可空 `vectorScore`/`bm25Score`/`rerankScore` 与各通道 rank（**加字段非破坏性；改 `score` 描述属语义变更，需契约重新批准**）。契约现描述 `检索相似度分数（cosine）`（`openapi.yaml:988`）。同时明确历史落库数据如何与新区分。
4. **重排开关的配置载体。** 「按请求」需给 `QAStreamRequest`/`DebugRetrievalRequest`/`EvalRunCreate` 加字段（契约变更）；「按知识库」需在 `knowledge_base` 表新增设置存储（**需 Flyway 迁移**）。二者需在 Stage 3 定，并在 §3 R2-R4 落地。
5. **`reviewTag` 枚举扩展 + CHECK 迁移。** R2-C5 的 7 类归因与现有闭集冲突：契约 enum `OK/WRONG_ANSWER/MISSING_EVIDENCE/WRONG_SOURCE/OTHER`（`openapi.yaml:1263`）+ 数据库 `chk_eval_run_item_review_tag`（`V1__init.sql:301`）。**扩展枚举 = 契约变更 + Flyway 迁移 + 前端类型重生成**（`pnpm gen:api`）。
6. **归因汇总与「已标记处理」的落点与聚合方式。** `eval_run_item` 现无 processed 字段（需明确复用 `review_note` 还是新增列）；且分页上限使客户端聚合不可行，**需服务端聚合端点**（与 §7.9 一并决定）。这是本轮最大的隐藏工程量。
7. **可比性指纹。** R2-C3 需要能区分「同配置同语料」与「同配置但语料已重入库/换分块策略」。建议在 `config_snapshot` 增记录分块数/标题路径快照或语料指纹，否则守卫查不出语料差异。
8. **耗时拆分的落点。** `eval_run_item` 现仅有端到端 `latency_ms`（`V1__init.sql:292`）；R2-L1 的检索/生成拆分与分位数需新增列或 JSON 字段（**迁移 + 契约**）。
9. **评测对比是否需服务端端点。** 同一数据集版本下 `seq` 1:1 对齐，**建议前端按 seq 关联**；但 R2-C5 的汇总（§7.6）大概率仍需服务端支持。二者一并决定。
10. **闭集枚举统一清点。** 除 `reviewTag` 外还有：`StreamEventStage.stage`（`openapi.yaml:1038-1051`，闭集 3 值）、`DebugIssue.type`（`:1120`，闭集 3 值，新增如 `CHANNEL_DEGRADED` 属契约变更）、`EvalCategory`、`ErrorCode`。任何扩展须同步契约 + 前端类型重生成。
11. **前端图表方案。** `rag-web` 现有依赖**无任何图表库**；R2-C2「指标变化」与 R2-C5「汇总」若以图表呈现需新增依赖，若走数字/表格则不需要。建议 Stage 2 原型阶段定。
12. **SSE 是否新增阶段事件**（如融合/重排阶段）：`stage` 为闭集，扩展属契约变更。

## 10. 验收与交付原则
