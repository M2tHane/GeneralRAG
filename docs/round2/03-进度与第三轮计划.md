## 1. 现在做到什么程度

### 1.1 一句话现状

两轮完成后，系统是一个**可本地运行、效果可测量、检索可解释**的知识问答 RAG：
文档入库 → 混合检索（BM25 + 向量 RRF 融合 + DashScope 重排，失败显式降级）→ SSE 流式回答（拒答时不给引用）→ 检索调试（分阶段位次）→ 效果评测（分块级判定、两次运行对比、可比性守卫）。

### 1.3 测试与质量现状

- 后端 `mvn test`：**130/130**（第一轮 109 → +21），连续 3 次全量连跑稳定；含 Testcontainers 集成套件与契约漂移测试。

- 中间验证过程中修掉的既有缺陷：SSE error 载荷前端解析错位（第一轮遗留）、`QaStreamIT` 断连测试既有的间歇性失败（根因：响应体小于 Socket 缓冲，服务端感知不到断连——已改为确定性触发设计路径）。

### 1.4 当前明确的技术债与局限（第三轮输入）

按影响排序：

1. **评测语料太小，结论外推性弱**：4 篇互不相干文档 / 29 分块 / 12 题。分块级判定恢复了区分度（随机基线 Hit@1≈0.034），但「Hit@1 0.5→1.0」只在极小语料上成立，**不能外推为通用检索能力**。这是当前最大的可信度短板。
2. **语料格式单一**：全部是 Markdown。BM25 通道的价值（精确术语/配置项/错误码）只在 MD 上被验证过；Word/Excel/CSV/复杂 PDF 完全未覆盖。
3. **存量语料重入库难**：内容哈希去重（`UNIQUE(kb_id, content_sha256)`）导致修复后必须「先删文档再重传」，删后 docId/chunkId 全变，历史评测的 retrieved/citations 里旧 chunkId 悬空。第一轮评测库（`a335d1f1…`）现在就是这种旧路径状态。
4. **数据集锚点与文件名耦合**：v2 数据集 evidence 用真实 titlePath（根 = 上传文件名），文档改名即失效；且每换一次分块策略就要重新生成数据集。没有更稳定的锚点键（如分块内容哈希）。
5. **拒答阈值的余弦口径不可靠**（数据限制）：VECTOR/降级场景的拒答正确率不能代表系统能力；只有重排生效时的数字可信。
6. **扫描件 PDF 不支持**：解析阶段异步检出后直接失败（`SCANNED_PDF_NOT_SUPPORTED`），无解析路径。
7. **查询改写未做**（第二轮显式搁置）：多轮指代追问仍只用当前问题向量化。当时无 BadCase 群体支持；这个前提可能已变化，第三轮需求收敛时重新评估。
8. **单实例**：入库任务靠进程内线程池 + DB 任务表；多实例化前需换消息队列。
9. **其他小项**：`Message.error.requestId` 不存档；会话标题默认「新会话」；冷启动首调 embedding 可达数秒（拉高分位数）。

## 2. 两轮走过的弯路（第三轮不再重复）

- **先修度量，再做优化**。第一轮在饱和指标上无法证明任何改进；第二轮一半工作量花在让评测说真话上。第三轮凡是涉及「效果提升」的主张，必须先确认指标有区分度。
- **能力建设要有配套语料**。BM25 做完后只有 MD 语料可测；第三轮做格式扩展时，新格式的评测语料/数据集要和能力一起交付，否则测不出价值。
- **接口位 ≠ 接入**。第一轮留了 Reranker 接口，实际接入时发现端点不兼容（OpenAI 兼容路径 404）、分数不可跨请求比较、与 minScore 量纲冲突——这些在需求收敛时都应作为独立事实核实，不能因为「接口位已留」就低估工作量。
- **大规模子代理并行的开销**（第二轮 Stage 2 单页代理最高烧了千万级 token）。第三轮涉及大量实现时，优先主 Agent 顺序实现 + 独立评审，只在真正独立的文件域上并行。
- **改构建必须重启服务再验证**。第二轮出现过「`pnpm build` 后旧进程持过期 manifest，CSS 404 整页裸奔」——验证 UI 必须包含样式真实加载的检查。

## 3. 第三轮计划（待需求收敛确认）

路线图方向（第一轮批准的 §8）：**解析与可靠性增强**。结合 §1.4 的技术债，我建议的优先级如下——**这是建议，不是决定**；第三轮 Stage 1 会重新收敛并交你批准。

### P1（建议 MVP 核心）：语料与格式的可评测扩展

1. **Word / Excel / CSV 解析**：按格式路由到新 `DocumentParser` 实现（接口位已留）。Apache POI 或等价库，Stage 3 定。
2. **配套评测语料**：每个新格式至少 2 篇真实结构文档 + 对应数据集条目（含分块级锚点），使新格式能力可被评测证明，而不是「跑通了就算」。
3. **稳定分块锚点键**（解决 §1.4-4）：给分块引入内容哈希或等价稳定键，数据集 evidence 优先用该键锚定，摆脱「文件名 + 分块策略」耦合。这是多版本管理的前置。

### P2：复杂 PDF / 扫描件（MinerU）

- 远端 HTTP 服务实现 `DocumentParser` 接口（表格、标题层级、页码定位）。
- **前置核实**：MinerU 的部署形态、资源需求、在本机的可行性——第二轮的教训是「接口位已留」不代表接入便宜。若本机跑不动，先做「远端服务 + 明确失败提示」的降级路径。
- 扫描件从「直接失败」变为「可解析」（资源允许时）或「明确引导」（不允许时）。

### P3：文档多版本管理

- 同名/同源文档的多版本上传、版本切换、按版本检索。
- 顺带解决 §1.4-3（重入库难、chunkId 悬空）：版本化后重新解析不需要删除重建。
- **依赖 P1-3 的稳定锚点**，否则数据集锚点在版本切换后再次失效。

### P4：可靠性增强

- 向量化失败补偿、历史版本残留清理、跨存储一致性策略明确化（文档化现有补偿语义 + 补齐缺口）。
- 分布式协调：**仍按需后置**，除非你明确要多实例。

### 重新评估项（不预设结论）

- **查询改写**：第二轮搁置的前提是「无 BadCase 群体」。第二轮对照实验里 VECTOR 基线 Hit@1=0.5 的 4 道失分题就是现成 BadCase——先做归因（P1 语料扩充后会更多），归因指向「问题表述」才立项，归因指向「检索本身」就不做。
- **第三轮不做的**（延续前两轮非目标）：登录/多租户/RBAC、消息队列（除非多实例）、LLM 裁判类生成侧指标（成本与归因复杂度，仍留 Later）。

### 顺序与理由

P1 → P2 → P3 → P4。理由：P1 同时缩小 §1.4-1 和 §1.4-2 两个最大短板，且为 P2/P3 提供评测地基；P3 依赖 P1-3；P4 大部分是文档化与补缺，可穿插。
