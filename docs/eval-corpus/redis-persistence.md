# Redis 持久化

## 1. 持久化方式概览

Redis 提供多种持久化选项：

- **RDB**（Redis Database）：按指定时间间隔对数据集做时间点快照。
- **AOF**（Append Only File，追加日志文件）：记录服务器收到的每一条写操作，重启时重放日志重建数据集。命令以 Redis 协议本身的格式记录。
- **无持久化**：完全关闭持久化，纯缓存场景使用。
- **RDB + AOF 同时开启**：可在同一实例上组合使用。

## 2. RDB 的优缺点

优点：

- RDB 是非常紧凑的单文件时间点表示，适合备份与容灾（可传到远端机房或 S3）。
- 最大化 Redis 性能：父进程只需 fork 子进程，由子进程完成全部持久化工作，父进程不做磁盘 IO。
- 大数据集下重启速度比 AOF 快。

缺点：

- 如果需要在 Redis 停止工作时尽量减少数据丢失，RDB 不合适。快照通常每五分钟或更久才做一次，宕机会丢失最近几分钟的数据。
- RDB 需要 fork 子进程：数据集很大时 fork 可能耗时，导致 Redis 停止服务数毫秒甚至一秒。

## 3. AOF 的优缺点与刷盘策略

优点：

- 更持久：有三种 fsync 策略可选（见下）。默认每秒 fsync，写性能依然很好，最多丢一秒数据。
- 追加式日志，无寻址、断电不易损坏；即使日志末尾写了半条命令，也可用 `redis-check-aof` 工具轻松修复。
- 文件过大时 Redis 会在后台自动重写（rewrite）：重写期间继续追加旧文件，同时生成包含重建当前数据集所需最小命令集的新文件，完成后原子切换。

缺点：

- 同样数据集下 AOF 文件通常比 RDB 大。
- 依 fsync 策略不同可能比 RDB 慢；`everysec` 下性能依然很高，`no` 下与 RDB 一样快。

### 三种 fsync 策略（appendfsync）

- `always`：每追加一条命令就 fsync。非常慢，也非常安全。支持多客户端/管道批量提交时合并为一次 fsync。
- `everysec`：每秒 fsync。足够快（2.4 起基本与快照同速），灾难时最多丢 1 秒数据。**建议且默认策略**。
- `no`：从不 fsync，交给操作系统。最快也最不安全，Linux 一般每 30 秒刷一次，取决于内核。

## 4. RDB 快照机制

默认 Redis 把数据集快照写到二进制文件 `dump.rdb`。可以配置「N 秒内至少 M 个键被修改则自动保存」，例如：

```
save 60 1000
```

表示 60 秒内至少 1000 个键变更则自动落盘，这种策略称为 snapshotting。也可以手动执行 `SAVE` 或 `BGSAVE`。

快照工作方式：Redis fork 出子进程；子进程把数据集写入临时 RDB 文件；完成后原子替换旧文件。依靠写时复制（copy-on-write）语义。

## 5. 如何选择

- 想要接近 PostgreSQL 程度的数据安全：同时使用 RDB 和 AOF。
- 能接受灾难时丢失几分钟数据、又很在意数据：可以只用 RDB。
- 官方不建议只用 AOF：定期有 RDB 快照对备份、更快重启、以及 AOF 引擎出 bug 时的兜底都有价值。

## 6. RDB 与 AOF 的相互作用

Redis 2.4 起避免 RDB 快照进行中触发 AOF 重写、或 AOF 重写进行中允许 BGSAVE，防止两个后台进程同时做重磁盘 IO。同时开启两者时，Redis 重启用 AOF 重建数据集，因为它保证是最完整的。
