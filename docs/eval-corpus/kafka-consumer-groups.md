# Kafka 消费者组与消息积压

## 1. 消费者组的核心规则

消费者使用消费者组（consumer group）名称标识自己。同一组内的规则：

- **一个分区只能被同一消费者组内的一个消费者消费**。
- 组内消费者数**不能超过订阅主题的分区数**：超出的消费者会分配不到任何分区而空闲空跑。
- 消费者数与分区数最好成整除关系，使分区均匀分配。
- 不同消费者组之间互不影响：每个组都能读到主题的全量消息。这是广播（多组）与队列（单组）两种语义的基础。

Kafka 把消费者组的成员关系与位移通过 **`__consumer_offsets` 内部主题**持久化：broker 端把每个分区的消费位移记录在该压缩主题中，组协调器（GroupCoordinator）负责成员管理与再平衡。

## 2. 再平衡（Rebalance）

- 消费者加入或退出组（进程重启、扩容、崩溃、心跳超时）都会触发分区的重新分配。
- 再平衡期间，整个组内的消费者停止消费，直到分配完成，因此频繁的再平衡会显著影响吞吐。
- 避免误判：调大 `session.timeout.ms`/`heartbeat.interval.ms` 的合理性、避免长时间 GC 暂停导致的心跳超时。

## 3. 消费位移与 Lag

- **Consumer Lag（消费者滞后量）= 分区日志的最新位移（LEO）− 消费者当前已提交/已消费的位移**，单位是消息数。
- Lag 是在**分区级别**监控的，通常在主题或消费组级别汇总展示。
- 例：分区最新位移 1000，消费者已消费 800，则 Lag = 200。

## 4. 积压的监控

- 命令行查看某消费组的分区级 Lag：

```
kafka-consumer-groups.sh --bootstrap-server <broker> --describe --group <group>
```

输出列包含 TOPIC、PARTITION、CURRENT-OFFSET、LOG-END-OFFSET、LAG、CONSUMER-ID 等。

- 也可以通过 JMX 指标监控（`kafka.consumer:type=consumer-fetch-manager-metrics,client-id=...` 下的 records-lag 等），接入 Prometheus 等监控系统做主题/组级汇总与告警。

## 5. 积压的常见原因与处理

常见原因：

1. 消费逻辑本身慢（下游接口超时、每条消息同步调外部服务）。
2. 消费者实例数少于分区数，并行度不足。
3. 消费者频繁再平衡，实际消费时间被打断。
4. 生产端流量突增。

处理手段按优先级：

1. **扩容消费者实例**——注意上限是分区数，分区不足时扩消费者无效；
2. 分区数确实不足时**增加分区数**（注意：增加分区会破坏按 key 的顺序性，且已有主题扩分区需谨慎）；
3. 排查并优化消费逻辑的慢调用；
4. 极端情况启用旁路：把非关键消息暂存后补偿处理，**不要用重置位移的方式跳过消息**（会丢数据）。

预防：

- 对主题级 Lag 设置告警阈值（如持续 > 5000 触发）；
- 压测消费逻辑确认单条处理耗时与分区并行度匹配。
